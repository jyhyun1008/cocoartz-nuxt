# 2. 업데이트

## 새 버전으로 올리기

이미지를 배포해서 쓰는 경우(기본 `docker-compose.yml`):

```bash
docker compose pull
docker compose up -d
```

소스를 직접 빌드해서 쓰는 경우(`docker-compose.yml`의 `build: .` 사용):

```bash
git pull
docker compose up -d --build
```

컨테이너가 새로 시작될 때마다 `docker-entrypoint.sh`가 **DB 마이그레이션을 자동으로 먼저** 돌린 뒤 서버를 띄워요. 즉 위 명령 한 번이면 코드 업데이트 + 스키마 반영이 다 됩니다 — 따로 마이그레이션 명령을 실행할 필요 없어요.

## ⚠️ 라이브 DB에는 `db:push`를 쓰지 마세요

이 저장소엔 두 가지 DB 동기화 방식이 있어요:

- **`npm run db:migrate`** — `server/db/migrations/*.sql` 파일들을 순서대로, 이력을 남기며 적용. `docker-entrypoint.sh`가 배포 때마다 쓰는 방식이 이거예요.
- **`npm run db:push`** — 지금 스키마(`schema.ts`)와 실제 DB를 직접 비교해서 차이만 맞춤. 이력을 안 남겨요. 로컬 개발 중 빠르게 스키마를 맞출 때 쓰라고 있는 명령이에요.

이 둘을 같은 DB에 번갈아 쓰면, `db:migrate`가 참조하는 이력 테이블(`drizzle.__drizzle_migrations`)이 실제 스키마 상태와 어긋나서, 나중에 `db:migrate`를 돌릴 때 "이미 있는 테이블/컬럼"과 충돌해 조용히 실패할 수 있어요(로컬 개발 DB에서 실제로 겪었던 문제 — `db:push`만 써오다가 `db:migrate`를 처음 돌렸더니 이력이 하나도 없어서 0번 마이그레이션부터 다시 적용하려다 막힘).

**그래서 라이브(운영) DB에는 항상 `docker-entrypoint.sh`를 통한 `db:migrate` 경로만 쓰세요.** `db:push`는 로컬 개발 DB 전용으로만 쓰고, 혹시 라이브 DB에 직접 `db:push`를 돌렸다면 그다음부터는 계속 `db:push`로만 맞추거나, `drizzle.__drizzle_migrations`에 지금까지의 마이그레이션 파일들을 수동으로 기록해서 이력을 다시 맞춰야 해요.

## SESSION_SECRET을 바꾸지 마세요

업데이트할 때 `docker-compose.yml`의 환경변수를 정리하다가 실수로 `SESSION_SECRET`을 새로 생성해서 넣지 않도록 주의하세요 — 이 값이 바뀌면 그 순간 전체 유저의 로그인 세션이 무효화돼요(설치 문서의 [1단계](./01-설치.md) 참고).

## 마이그레이션이 실패했다면

`docker compose logs app`으로 `docker-entrypoint.sh`가 마이그레이션 단계에서 에러를 냈는지 먼저 확인하세요. 실패하면 서버 자체가 안 뜨니(마이그레이션이 서버 시작보다 먼저라서) 바로 알아챌 수 있어요.
